## 2. 实现方案

### 2.1 图集构建(`tools/build_atlas.py`)

- 分组:misc(idle/walk/click 8 张单帧)+ 每个 ACTIONS 动作一组,共 10 组
- 分片:单片宽度上限 **16384px**(512 高时峰值 ~33MB/片;raster 下安全),大动作自动续片:
  pace 192 帧 → 6 片,spin 120 帧 → 4 片,recoil 60 帧 → 2 片,其余各 1 片
- 索引:`atlas_index.json`:`{version, max_strip_w, frames: {帧名: [文件, x, y, w, h]}, order}`
- 无损:PIL 逐帧 `paste` 不重采样,`--verify` 逐帧字节级比对源图 —— **500 帧 ALL PASS**
- 体积:源 74.3MB → 图集 72.8MB(PNG 重压缩微降)

### 2.2 加载链路(`main.py`,三层回退)

```
缓存 strip(热启动)→ 图集(冷启动)→ 散帧文件(兜底)
```

- `_load_atlas_index()`:读索引,损坏/缺失返回 None → 走散帧老路径
- `_frame_names()`:图集模式帧清单来自索引(不再探测散帧目录)
- `_cache_signature()`:图集模式下指纹 = 索引 + 全部图集文件的 size/mtime
  (图集任何变动 → 预缩放缓存自动失效重建,实测通过)
- `_load_atlas_frames(phys)`:**多线程解码**(QImage 允许非 GUI 线程,PySide6 释放 GIL),
  8 线程把 19 个文件的全量 PNG 解码从 2.19s 压到 **0.51s**;主线程 `QPixmap.fromImage`
  转换 + `copy()` 切帧 + `scaledToHeight(phys)`,边解码边消费控制峰值内存

### 2.3 性能实测(跨进程,`tools/probe_startup.py`)

| 场景 | 图集化前 | 图集化后 |
|---|---|---|
| 冷启动(无缓存) | 3.08s | **0.82s** |
| 二次启动(缓存命中) | 0.15~0.21s | 0.13~0.21s(不变) |
| 后台缓存构建 | 0.78s | 0.79s(不变,不阻塞) |
| 缓存磁盘占用 | 4MB | 4MB |

### 2.4 关键剖析结论(为什么不是"减文件数"这么简单)

微基准(`bench`,已清理):
- 19 个图集文件**单线程全量解码 2.38s** ≈ 500 散帧解码 2.89s ——
  瓶颈是 **PNG 解码 524MB 原始像素**(500×512×512×4),与文件数无关
- `QImageReader.setScaledSize` 解码期缩放:2.64s,**不加速**(Qt 先全解再缩)
- WebP 解码更快,但 **Qt 6.11.2 的 WebP handler 解大图会原生崩溃**(进程直接死),排除
- 最终解法:**8 线程并行 QImage 解码** 0.51s(4.3×)+ 主线程切帧缩放 0.3s ≈ 0.82s
